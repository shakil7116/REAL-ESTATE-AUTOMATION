## 2. Per-Page Code Audit

### 2.1 Dashboard (`src/app/(dashboard)/dashboard/page.tsx`)

**Verdict: 1 critical, 2 warnings**

- **CRITICAL** — Arabic heading typo at line 175:
  ```tsx
  const heading = lang === 'ar' ? 'محفكتك، بوضوح.' : 'Your portfolio, in focus.';
  ```
  Should be `محفظتك` (portfolio), not `محفكتك` (nonsense word). This is a typo that will confuse Arabic-speaking users.

- **WARNING** — No RTL `dir` attribute on the top-level div. The dashboard uses flex layouts with fixed `start`/`end` positioning (e.g., `start-3`/`end-3` on stat cards). These are handled via the parent layout's RTL logic, but individual child components should opt into RTL properly via `dir` or use logical properties.
- **WARNING** — `activityData` switches between hardcoded EN and AR arrays (`RECENT_ACTIVITY_EN` / `RECENT_ACTIVITY_AR`). These are mock data and will disappear once the real API connects, but the empty-state path shows nothing (no explicit empty state for when `stats.totalRevenue === 0` and activity list is still rendered). The page renders static activity items even when there are zero revenue/tickets, which looks like fake data.
- **Nice-to-have** — Consider showing a genuine empty state ("No data yet — connect your first property") when `totalRevenue === 0`.

### 2.2 Properties (`src/app/(dashboard)/properties/page.tsx`)

**Verdict: 2 critical, 3 warnings**

- **CRITICAL** — Double `<PageHeader>` component at lines 133 and 146. The first has a title+subtitle; the second is called just to render an action button (`New Property`) with empty title/subtitle. This produces two headers on the page visually.
- **CRITICAL** — `handleCreate` toast notification uses template literals directly instead of i18n keys. While the notification uses `tr()` for the message string, the `notifyChange` payload mixes English and Arabic inline:
  ```tsx
  notifyChange('property_created', tr(`Property "${form.name}" created`, `تم إنشاء العقار "${form.name}"`));
  ```
  This is correct usage. However, the success/failure paths silently catch all errors (`catch { /* error handled */ }`) with no user-visible feedback if the API call fails.
- **WARNING** — Search filter does `.toLowerCase()` on `p.address` and `p.city` without null checks. If these fields are undefined, the code crashes. Should guard with `(p.address ?? '').toLowerCase()`.
- **WARNING** — `property.name.toLowerCase()` also lacks a null guard.
- **WARNING** — The "Health" label for properties uses a hardcoded English map (`HEALTH_AR`) but the keys are English ("Healthy", "Attention", "Maintenance"). If a new status is added in the code, the Arabic translation won't exist and will show the English fallback.

### 2.4 Payments (`src/app/(dashboard)/payments/page.tsx`)

- **CRITICAL** — Hardcoded English "PDC" in the payment method dropdown at line 112:

  PDC is a Qatar-specific term (Post-Dated Cheque). It should be localized as `tr('PDC', 'شيك مؤرخ')` or similar. In Arabic, users expect to see الشيك المؤرخ or شيك, not the English abbreviation.

- **WARNING** — `p.amount.toString().includes(search)` at line 78 allows partial numeric matches (searching "5" matches "5000" and "15"). Acceptable UX but worth noting.
- **WARNING** — The date inputs (`payment_date`, `due_date`) have no locale formatting. They show raw ISO dates like "2025-01-15" instead of formatted dates. In RTL mode, Arabic users might expect `15 يناير 2025`.
- **WARNING** — No keyboard accessibility for the `showForm` toggle (it's a `<button>` so this is fine), but there's no `aria-label` on the search icon inside the search input.

### 3.3 RTL Support (`ltr:`/`rtl:` class usage)

Checked for ltr-specific classes that break RTL:

**Correctly handled:**
- `ltr:right-3 rtl:left-3` — used in login, signup, forgot-password pages for icon positioning
- `ltr:ps-10 rtl:pe-10` — not consistently used; some inputs use `ps-10` (padding-start) which is RTL-aware
- `rotate-180` on ChevronRight — correctly toggled based on `isRtl` in all pages checked

**Problems found:**
- `payments/page.tsx` line 143: `<Search className="absolute left-3 top-1/2 -translate-y-1/2 w-4 h-4 text-slate-400" />` — uses `left-3` (physical left) instead of `start-3` (logical). In RTL, the search icon appears on the right side of the input, which is wrong — it should be on the start (left in LTR, right in RTL) side. **RTL bug.**
- `payments/page.tsx` line 144: `<input ... className="w-full pl-10 pr-4 ..."` — uses physical `pl-10` (padding-left) instead of `ps-10` (padding-start). In RTL, the input text starts at the right but the padding keeps the text pushed from the left, causing overlap with the icon. **RTL bug.**
- `properties/page.tsx` line 195: `<Filter className="absolute start-3 top-1/2 -translate-y-1/2 w-4 h-4 ..."` — correctly uses `start-3`. Good.
- `leads/page.tsx` line 155: `<input ... className="w-full pl-10 pr-4 ..."` — same `pl-10` bug as payments. **RTL bug.**
- `units/page.tsx` line 280: `<input ... className="w-full input-field pl-10 pr-4 ..."` — same `pl-10` bug. **RTL bug.**
- `GlobalCopilot.tsx` line 191: `pl-4 pr-5` — physical padding in a chat-like component. Should use `ps-4 pe-5`. **RTL bug.**
- `copilot-panel.tsx` line 286: `ml-1` — physical margin. Should be `ms-1`. **RTL bug.**
- `layout.tsx` line 183: `<kbd ... ml-2>` — physical margin in keyboard shortcut display. Not critical but inconsistent.
- `layout.tsx` line 243: `text-right pl-2 border-l ml-1` — mixed physical and logical. The `border-l` and `ml-1` should be `border-s` and `ms-1` for RTL. **RTL bug.**
- `RevenueChart.tsx` line 82: `ml-auto` — used for a delta badge. In RTL this pushes the badge to the left instead of right. **RTL bug.**
- `page.tsx` (marketing) line 311, 420: `text-left` and `ml-auto` — marketing page, less critical since it may not be in RTL, but should still be fixed.
- `Signup page` line 431: `text-left` for plan card — should be `text-start`.
- `Tenants page` line 170: `text-end` — should be `text-end` (this one is actually OK since `text-end` is a Tailwind logical class... wait, no — `text-end` IS a physical direction class in Tailwind v3. It renders as `text-align: end` which is actually correct in modern browsers. This is fine.)

**Summary of RTL bugs:** 7 locations with physical-direction classes that break in RTL mode.
