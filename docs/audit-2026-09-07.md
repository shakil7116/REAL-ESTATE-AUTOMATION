## P0 — Blocking

### 1. Production build fails: illegal export in a route module

`src/app/api/auth/[...nextauth]/route.ts:13` exports `getUserByEmail`. Next.js
App Router permits only the HTTP verb handlers plus a fixed config allowlist to be
exported from a `route.ts`. The generated route type check rejects it:

```
Type error: Property 'getUserByEmail' is incompatible with index signature.
  Type '(email: string) => Promise<any>' is not assignable to type 'never'.
Next.js build worker exited with code: 1
```

`tsc --noEmit` does **not** catch this — it runs before Next generates
`.next/types/**`. Any claim of "TS clean, ready to ship" based on `tsc` alone is
unreliable for this codebase.

**Fix:** move `getUserByEmail` into `src/lib/auth.ts` (or `src/lib/database.ts`,
per `AGENTS.md` @backend-eng scope) and import it into the route.

### 2. Authentication is bypassable, and the middleware is inverted

`src/lib/withAuth.ts` is the single gate in front of every `protectedHandler`
route (18 of 21 routes). Compounding defects:

**a. JWT signatures are never verified.** `decodeNextAuthToken()` splits on `.`,
base64url-decodes the middle segment, and trusts it. The in-code comment argues
this is safe because the cookie is HttpOnly and same-domain — but the function is
*also* used for the `Authorization: Bearer` path (`withAuth.ts:76-82`), where no
cookie protection applies. An unauthenticated attacker can mint a three-segment
token whose middle segment is `base64url({"id":"x","role":"owner"})` and receive
full authenticated access to every protected route. This is a trivially
exploitable total auth bypass.

**b. `exp` is decoded but never checked.** Expired sessions remain valid forever.

**c. Real NextAuth v4 cookies likely never validate.** NextAuth v4 defaults to an
encrypted JWE session token (5 segments). The `parts.length !== 3` guard rejects
it, so genuine cookie sessions silently fall through to `null`.

**d. `src/middleware.ts:29` blocks the entire API unconditionally.**

```js
if (pathname.startsWith('/api/') && process.env.NEXTAUTH_DEMO !== 'true') {
  return 401;   // <- no session check whatsoever
}
```

There is no session lookup in this branch. With `NEXTAUTH_DEMO` unset (i.e.
production), **every API route returns 401 to every caller, including
legitimately logged-in users.** The only way the app functions is
`NEXTAUTH_DEMO=true` — which makes `getSession()` return a hardcoded `owner`
user (`withAuth.ts:56-63`) and disables auth entirely. The system has exactly two
states: fully broken, or fully open.

**e. Dashboard pages are unprotected.** `middleware.ts:44-50` reads the session
cookie and the redirect is commented out with `// In production, uncomment`.

**Fix:** verify tokens with `next-auth/jwt`'s `getToken({ req, secret })` rather
than hand-rolled decoding; check `exp`; make the middleware branch on an actual
session; gate `NEXTAUTH_DEMO` behind `NODE_ENV !== 'production'`; restore the
page redirect. **This touches auth — `CLAUDE.md` §9 requires sign-off before
changes.**

### 3. CI has never executed

- `git remote -v` is empty. There is no remote; nothing has ever been pushed.
- `.github/workflows/ci.yml` triggers on `[main, develop]`. The only branch is
  `master`.

So the secret scan, i18n parity check, build, tests and the `all-green` required
check are decorative. Worse, the pipeline would fail immediately if wired up:

- **Web `npm run lint`** — no `.eslintrc*` exists in `propertyease/`. `next lint`
  drops into an interactive "How would you like to configure ESLint?" prompt and
  hangs or fails in CI.
- **Mobile `npm run lint`** — `propertyease-mobile/package.json` has **no `lint`
  script at all**. The step dies with "Missing script: lint".

**Fix:** add `.eslintrc.json` (`{"extends":"next/core-web-vitals"}`) to the web
app, add a `lint` script to mobile, add `master` to the branch filter, and add a
remote.

## P1 — Serious

### 4. Server-only code is bundled into client components

`next build` emits:

```
./src/lib/database.ts   Module not found: Can't resolve 'fs'
  -> ./src/app/forgot-password/page.tsx
./src/lib/seed.ts       Module not found: Can't resolve 'fs'
  -> ./src/app/login/page.tsx
```

`src/app/login/page.tsx:1` is `'use client'` and line 12 imports
`seedSampleData` from `@/lib/seed`, which reaches `fs`. Webpack stubs `fs` to
empty in the browser, so these paths silently no-op at runtime rather than
erroring — a data bug hiding behind a build warning. It also violates the
`AGENTS.md` @frontend-eng boundary (client pages must not reach `database.ts`).

### 5. `POST /api/debug/reset` ships to production, unauthenticated

`src/app/api/debug/reset/route.ts` mutates global application state
(`globalThis.__PE_FALLBACK__`) with no `protectedHandler`, no role check, and no
`NODE_ENV` guard. It is currently shielded only by the accidental blanket
middleware 401 (defect 2d) — the moment that is fixed correctly, this becomes a
public state-reset endpoint. It also returns `{success, error}`, not the contract
envelope.

### 6. `/api/copilot` is a public, unauthenticated LLM endpoint

`middleware.ts:18` lists `/api/copilot` in `PUBLIC_PATHS`, and the route does not
use `protectedHandler`. Anyone can drive paid model calls through it. There is no
rate limiting anywhere in the codebase.

### 7. Evals have never measured the real engine

The harness passes 14/14 — but only under `PE_EVAL_STUB=1`, where it compares
deterministic stub strings to themselves. The runner explicitly prints
`Skipping baseline regression check (STUB MODE)`. CI hardcodes stub mode too. So
`evals/baseline.json` has never been validated against `minimax-m3-free`, and
`CLAUDE.md` §12's engine-swap procedure ("run `npm run eval` to compare new engine
against baseline") has no data to compare against. The eval infrastructure is
sound; it has simply never been pointed at a model.

### 8. Rule 6 test coverage is unmet

`CLAUDE.md` §6 Rule 6: *"tests required for auth, payments, lease creation,
ticket lifecycle."* The web suite is `src/lib/db.test.ts` and
`src/lib/i18n.test.ts` — **zero of the four mandated areas are covered**, across
21 API routes, 21 pages and 25 components.

## P2 — Hygiene

### 9. Env vars used in code but absent from `.env.example` (Rule 4)

14 undocumented, including the security-critical ones. A deployer following
`.env.example` ships with **no `NEXTAUTH_SECRET`**:

```
GOOGLE_CLIENT_ID          GOOGLE_CLIENT_SECRET      NEXTAUTH_DEMO
NEXTAUTH_SECRET           NEXT_PUBLIC_ANALYTICS_ENGINE
NEXT_PUBLIC_SENTRY_DSN    SENTRY_DSN                SENTRY_ORG
SENTRY_PROJECT            NEXT_PUBLIC_VERCEL_ENV    VERCEL_ENV
VERCEL_GIT_COMMIT_SHA     NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA    NODE_ENV
```

Conversely, everything *in* `.env.example` is correctly described in
`docs/ENV.md` — the sync only breaks in one direction.

### 10. Conventional-commit violations (Rule 5)

Three commits carry a stray leading `@`: `@chore(docs):`, `@chore:`, `@fix(build):`.
The `.githooks/` pre-commit hook does not catch this.

### 11. Root `.gitignore` omits `node_modules/` and `.next/`

Both appear as untracked noise in `git status` at the root.
`propertyease/.gitignore` covers its own subtree, but the root workspace and
`propertyease-mobile/` rely on it being absent. Nothing sensitive is tracked
(verified: 0 tracked matches for `node_modules`, `.next/`, `.env*`,
`settings.json` across 105 tracked files).

### 12. Stray files at repo root

`UsersHpAppDataLocalTempactivities.json` (34 bytes, malformed name from a shell
redirect), `replace-runner-stub.js`, `test-stub.js`.

### 13. Envelope contract drift

`contracts/api-envelope.md` defines 10 canonical error codes and an optional
`messageAr`. `withAuth.ts` `errResponse()` hardcodes `code: 'INTERNAL_ERROR'` for
**every** failure regardless of status, and never emits `messageAr`. Validation
failures return 400 where the contract specifies 422 `VALIDATION_FAILED`.

### 14. Sentry misconfiguration

Build warns that `sentry.server.config.ts` and `sentry.edge.config.ts` must move
into an `instrumentation.ts` `register()` hook for the SDK to work. There is no
`global-error.js`, so React render errors are not reported.

## What is genuinely solid

Worth stating plainly, because it is the majority of the system:

- **i18n is exemplary** — 216 EN keys, 216 AR keys, zero drift, centralized in
  `src/lib/i18n.ts` exactly as Rule 3 demands.
- **The envelope pattern is real and well-adopted** — `protectedHandler` /
  `okResponse` / `errResponse` plus `validate()` with zod schemas in
  `src/lib/validators.ts` covers 18 of 21 routes cleanly. The abstraction is
  right; only the auth internals and error codes are wrong.
- **Rules 7 and 8 are honoured** — `reactStrictMode: true`, and `/_next/static/*`
  correctly uses `max-age=31536000, immutable` with a documented rationale for why
  the previous `no-store` was wrong.
- **Service worker v5** correctly refuses to fall back to cached `/`.
- **The AI-OS scaffolding is coherent** — `CLAUDE.md`, `AGENTS.md`, 6 agent
  contracts, versioned prompts, eval schema, MCP registry, skills and commands are
  all present and internally consistent.
- **Mobile is clean** — 0 TS errors, 28/28 tests.

The architecture and contracts are in better shape than the enforcement around
them. Every P0 here is an *enforcement* failure: gates that exist on paper but
have never run.

1. Fix the build (defect 1) — one-line move, unblocks everything.
2. Add `.eslintrc.json` + mobile `lint` script, add `master` to CI triggers, add a
   remote (defect 3) — makes every future gate real.
3. Auth rewrite (defect 2) — **requires sign-off per `CLAUDE.md` §9**.
4. Guard `/api/debug/reset` and `/api/copilot` (defects 5, 6).
5. Untangle client/server imports (defect 4).
6. Backfill `.env.example` (defect 9).
7. Run evals against the real engine once, and record the baseline (defect 7).
8. Tests for auth / payments / lease creation / ticket lifecycle (defect 8).
